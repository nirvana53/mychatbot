# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An internal-only Streamlit chatbot for querying quarterly consolidated financial closing (결산) data. It answers natural-language questions by parsing them with rule-based logic, querying a local SQLite database, and formatting the result — no cloud LLM is called. Budget is 0원; the whole stack is free/open-source and must never call out to the public internet (security-sensitive internal data, same-본부 access only). See `PRD.md` for the full product requirements.

## Commands

```powershell
pip install -r requirements.txt        # install deps (streamlit, pandas, openpyxl, altair)
python -m data_pipeline.generate_sample_data   # (re)generate synthetic quarterly Excel files into data/raw
python -m data_pipeline.ingest          # (re)load data/raw/*.xlsx|*.csv into data/finance.db — run after any data change
streamlit run app.py                    # launch the chat UI (also re-runnable from the sidebar "결산 데이터 다시 적재" button)
```

There is no test suite, linter, or build step configured. Verify changes by re-running ingest and exercising `chatbot.answer("...")` directly from a `python -c` snippet, or by launching Streamlit and checking `streamlit.log` for exceptions.

## Architecture

Pipeline: **question → `query_engine/nlu.py` (parse) → `query_engine/query.py` (SQLite aggregate) → `llm/` (phrase as text) → `chatbot.py` (assemble chart + follow-up suggestions) → `app.py` (render)**.

- **Data model**: `data/finance.db` has one table, `financial_statements`, with columns `year, quarter, statement_type, entity, level1, level2, level3, amount`. Accounts are a **3-level tree** (대분류/중분류/세부계정, e.g. 매출→제품매출→국내제품매출). `entity` holds either one of 20 legal-entity codes (법인01…법인20) or `연결조정` (consolidation elimination entry). **There is no stored "연결" row** — consolidated figures are always computed on the fly by summing across all entities with no entity filter; passing a specific entity name filters to that single subsidiary (drill-down). This invariant (법인 20개 합산 + 연결조정 = 연결) is enforced at generation time in `generate_sample_data.py`, not by a stored total.
- **Computed metrics vs. ratio metrics**: 매출총이익/영업이익/당기순이익 (`level="metric"`) are formulas over signed level1 sums, defined in `query_engine/query.py::COMPUTED_METRICS`. 영업이익률/매출원가율/부채비율/ROE/ROA (`level="ratio"`) are a second tier defined in `RATIO_METRICS` as `(numerator_name, denominator_name)`, where each side is resolved recursively (metric-or-level1) and the result is `numerator/denominator*100` with `unit="%"`. `query.get_amount()` branches on `level` first for `"ratio"` (recursing into itself) before falling through to the metric/leaf-sum paths. Anything downstream that formats amounts (`llm/mock_client.py::_fmt`) must special-case `unit == "%"` (1 decimal, no thousands-style rounding) and must never mix percentage-of-a-percentage with percentage-point deltas — see `_change_phrase`'s `%p` branch.
- **ingest.py column matching is fuzzy by design**: it looks for columns whose *names contain* keywords (법인/대분류/중분류/세부계정/금액, plus English fallbacks) rather than requiring exact headers, and infers year/quarter from the filename via regex. This is intentional so real company files with slightly different headers/filenames still load — adjust the `*_KEYWORDS` lists and `_extract_period()` regex in `data_pipeline/ingest.py` rather than restructuring the pipeline. `ingest()` drops and recreates the table every run (always rebuilds from whatever is currently in `data/raw`).
- **nlu.py is intentionally rule-based, not an LLM call**: it extracts absolute periods (regex), relative periods (이번분기/작년 etc., resolved against `query.get_periods()`), an explicit **date range** (`"X부터 Y까지"`, `_extract_period_range()`), one or more entity mentions, and a target/level via longest-substring match against `query.list_accounts()` (which returns `{level1, level2, level3, metrics, ratios}`) plus a small alias table (순이익→당기순이익, 판관비→판매비와관리비, ROE/ROA aliases, etc.). Matching is **whitespace-normalized and typo-tolerant**: `_normalize()` strips all whitespace before substring matching (so "영업 이익" still matches "영업이익"), and `_fuzzy_contains()` (difflib `SequenceMatcher`, ratio ≥ 0.75) is tried as a fallback only after exact matching fails on both target and entity lookups — this is a deliberate precision/recall tradeoff for a small internal user base, not a general-purpose fuzzy search. `_keyword_hit()` applies the same whitespace normalization to multi-word keyword lists (e.g. `NEW_ACCOUNT_KEYWORDS` containing "신규 계정") so "생긴계정" (no space) still matches "새로 생긴". Intent detection order matters: list_accounts → **when no target/account name is matched at all**, check `NEW_ACCOUNT_KEYWORDS` ("새로 생긴 계정" → `new_accounts`) and `ANOMALY_KEYWORDS` ("이상치 계정" → `account_anomaly`) before falling back to a **`followup_context`-based re-resolution** (see below) and only then to `unresolved` → compare_entities (2+ entity names mentioned in one question, short-circuits everything below) → breakdown_entity/breakdown_account (keyword-triggered; breakdown_entity also fires on 이상치/특이/튄-style anomaly keywords **when a target *is* present**, setting `outlier_only=True` — this is entity-level anomaly detection and is a different intent from the target-less `account_anomaly` above) → period-range trend (`"X부터 Y까지"`, forced before the compare check below so its two boundary periods don't get treated as a 2-period comparison) → compare (triggered by *any* 2 periods found, not just an explicit "비교" keyword) → trend (keyword or no period given) → single. When editing intent logic, preserve this order or later branches will shadow earlier ones.
- **`followup_context` lets a question omit the account name entirely** (e.g. "2025년 1분기랑 비교해줘" with no account mentioned): `chatbot._snapshot_followup(context)` captures `{target, level, entity, year, quarter}` from whichever single point a resolved answer ultimately referred to (the latest row for `trend`, `point_b` for `compare`, etc.) and returns it as `result["followup_context"]`; `app.py` stores it in `st.session_state.followup_context` and only overwrites it when a new snapshot is non-`None` (so an `unresolved` or `list_accounts` turn doesn't erase the standing context). `nlu.parse_question()` accepts this dict as its last positional argument and, **only when the question's own target lookup came back empty**, borrows the target/level/entity from it and treats any period mentioned in the new question as the second point of a `compare` (or as a `single` lookup if the mentioned period equals the remembered one). This is deliberately a single-slot memory (last resolved point only), not a conversation history.
- **LLM backend is swappable, not yet connected**: `config.ACTIVE_LLM_BACKEND` selects between `llm/mock_client.py` (current default — offline, template-based, must stay dependency-free of any network call) and `llm/internal_agent_client.py` (placeholder for the company's internal AI agent API — endpoint/auth/model in `config.INTERNAL_AGENT_CONFIG`, currently empty). Both implement `llm/base.py::LLMClient.generate_answer(question, context)`. `chatbot.py` only depends on this interface, so swapping backends should never require touching `chatbot.py`, `nlu.py`, or `query.py`. When the internal agent API becomes available, fill in the three TODO-marked methods in `internal_agent_client.py` (`_build_payload`/`_call_api`/`_parse_response`) rather than changing the calling convention.
- **`chatbot.answer(question, user="", followup_context=None)` returns a dict**, not just text: `{"text": ..., "chart": {...} | None, "table": [...] | None, "suggestions": [...], "followup_context": {...} | None}`. The caller (`app.py`) is responsible for round-tripping `followup_context` between calls (see the `followup_context` bullet above) — `chatbot.py`/`nlu.py` never persist it themselves. `chart` is a plain dict (`{"type": "line"|"bar", "rows": [...], "label": ..., "unit": ...}`) built by `chatbot._build_chart()` — the actual Altair chart object is only constructed in `charts.py`, kept out of `chatbot.py` so the orchestrator has no visualization dependency. `table` is a plain list-of-dicts (Korean column names) built by `chatbot._build_table()`, one branch per intent, purely for `app.py` to hand to `pandas.DataFrame(...).to_csv()` behind a download button — it has no other consumer, so don't route it through the LLM layer. `suggestions` are plain Korean question strings generated per-intent in `chatbot._build_suggestions()`; they are valid input to the same `nlu.parse_question()` path — clicking one in the UI just resubmits it as if typed, so no separate handling code exists for suggestions. For `single`, `chatbot._build_context()` also attaches `context["changes"]` (QoQ/YoY deltas from `query.get_period_comparisons()`); for `compare` on a level1/level2 target it attaches `context["contributors"]` (per-subaccount diff between the two periods, from `query.compare_subaccount_contributions()`, largest `abs(diff)` first) so the mock client can explain *what* moved, not just by how much.
- **app.py auth captures a name/사번 alongside the shared password**, but it is still not real per-user auth: `auth.py`'s password check is unchanged (single shared secret in gitignored `auth_config.json`), and the name typed at login is trusted as-is (no verification) and stored only in `st.session_state.user_name` for the session. It exists solely so `data/query_log.csv` rows (columns: `timestamp, user, question, answer, status`) can be attributed to a person for audit purposes — `status` is `"resolved"` unless `nlu.parse_question()` returned `intent="unresolved"`. The sidebar's "최근 미해결 질문" expander reads this same CSV back with `pandas.read_csv` and filters `status == "unresolved"`; if you change the log's column order or names, update that filter too.
- **Streamlit suggestion/FAQ-button pattern**: `app.py` uses a `st.session_state.pending_prompt` variable to let a clicked suggestion or sidebar FAQ button behave like typed `st.chat_input`, followed by `st.rerun()` after appending the assistant message so the history loop (not the inline block) is the single source of rendering — don't add a second render path when touching this file. Because sidebar FAQ buttons can set `pending_prompt` before the main body runs, `st.session_state.messages`/`pending_prompt` are initialized once near the top of the script (right after the auth gate), not lazily right before the render loop — keep that ordering if you add more sidebar controls that touch session state.

## Data/network boundaries (do not relax without asking)

- Nothing in this codebase should make an outbound network call except the not-yet-implemented `internal_agent_client.py`, and that must only ever point at an internal company endpoint.
- `.streamlit/config.toml` disables usage-stat telemetry (`gatherUsageStats = false`) — keep it disabled.
- Real financial data belongs only in `data/raw/` and `data/finance.db`, both gitignored; don't add code that copies/exports this data elsewhere.
